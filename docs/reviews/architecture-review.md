# Architecture review: internal BPO operations analytics

Status: planning recommendation, 12 September 2026. Based on all three original project PDFs. Hardware, identity provider, workforce size and integrations are assumptions to validate through a small technical pilot, not facts established by the sketches.

## Decision

Build a single-company application with a Windows C#/.NET collector, ASP.NET Core modular monolith (API and background worker), React/TypeScript portal and one self-managed PostgreSQL database. Use existing company infrastructure and identity where available. No ClickHouse, Kafka, Redis, Kubernetes, paid analytics or production LLM dependency in MVP. PostgreSQL is available under its permissive license; operating, securing and backing up the deployment still consumes resources. [PostgreSQL license](https://www.postgresql.org/about/licence/)

Keep domain modules and interfaces separate in code: identity/organization, endpoint enrollment, telemetry ingestion, interval processing, roster/schedule imports, operational outcomes, classifications, reporting, corrections and audit. Deploy API and worker from one codebase; initially they can share a host. PostgreSQL transactions and a durable database job table replace a message broker. Polling dashboard refresh every 60 seconds is adequate initially. Internal reverse proxy terminates TLS; database has no public port. A private network/VPN is the assumed access route, including remote endpoints.

The original assertion that a conventional database must fail is unsupported. Select infrastructure after measuring event shape and throughput. Avoid mistaking desktop activity for productivity, payable time or completed work.

## Endpoint collection and transport

Run the collector in each interactive Windows user session. A small optional service performs installation/update and transport duties through authenticated, access-controlled local IPC. A service in Session 0 cannot simply observe every user's desktop: Windows input APIs and service isolation require a per-session design. [GetLastInputInfo](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getlastinputinfo), [Interactive services](https://learn.microsoft.com/en-us/windows/win32/services/interactive-services)

Collect foreground application identity, last-input-based idle state, lock/unlock, session start/end and sleep/resume. Default to no keyboard hooks, key counts, mouse counts, screenshots, window titles, URL paths, clipboard or document contents. A browser process does not reveal which site is used: show browser usage as unclassified unless a separately reviewed domain-only extension is later justified. An approved work application is an operational classification, not proof of productive output.

Initial engineering parameters: sample idle/foreground fallback every 5 seconds; use state-change notifications where reliable; package application/state durations in 60-second buckets, retaining subinterval offsets needed for overlap reconciliation; batch uploads every 60 seconds with jitter, or on a capped buffer threshold. Collection frequency, stored interval length and upload batch frequency are distinct. Faster application switching can produce many intervals per minute, so the sizing model below is explicitly an assumption, not a bound. Reduce granularity or aggregate locally if measured rates exceed budget; never silently throw away coverage.

Use SQLite as a durable outbound queue. Encrypt payloads before writing, with a random data key protected by Windows DPAPI scoped to the owning account and restrictive ACLs; SQLite by itself is not encrypted. Keep metadata minimal, avoid identifiers in logs, and test reboot/user-profile/key-loss recovery. DPAPI protects local stored secrets but is not protection from a privileged compromised endpoint. [Microsoft data protection](https://learn.microsoft.com/en-us/dotnet/standard/security/how-to-use-data-protection)

Target seven days offline, with a 100 MB local cap as an initial configurable guardrail. At cap, surface degraded health, preserve an explicit lost-coverage marker and follow documented oldest-first eviction; never label missing telemetry as idle. Server acknowledges only after durable commit; delete only acknowledged records. Retry transient errors with exponential backoff and jitter. Support explicit per-record accepted/duplicate/quarantined/rejected acknowledgments, bounds on count and uncompressed size, and a permanent-error quarantine so one poison event cannot block the queue. Do not permit a replay to change identity or event content.

## Event contract and correctness

Each immutable event carries `schema_version`, `event_id` (random UUID), `device_id`, `employee_id` resolved from enrollment, `boot_id`, `os_session_id`, `collector_instance_id`, monotonic `sequence`, `event_type`, UTC start/end, monotonic start/end/duration, application registry key where applicable, state, policy version and agent version. Server adds `received_at`, validation status and time-quality flags. Device credentials bind employee/session assertions to enrolled assignments; never trust a submitted employee ID alone. A desktop employee and a portal login are separate entities.

Start unpartitioned with unique `event_id` and unique `(device_id, collector_instance_id, sequence)`. Store payload hash; duplicates with matching content are harmless, conflicting duplicates are rejected and audited. In one transaction persist events and affected-day work items; workers recompute deterministic employee-day aggregates with versioned formulas. Crash/replay must never increment totals twice. If monthly partitioning becomes warranted, explicitly redesign uniqueness: PostgreSQL requires partition keys in unique constraints; a small unpartitioned receipt ledger can preserve global deduplication across raw partitions. Keep receipts for the allowed replay horizon and reject expired events; do not claim global UUID uniqueness from a partition-local index. [PostgreSQL partitioning limitations](https://www.postgresql.org/docs/17/ddl-partitioning.html)

Use monotonic elapsed time for duration and server handshakes to estimate wall-clock offset. Device time is evidence, not authority. Flag drift above an initial two-minute tolerance, impossible durations and future events; quarantine rather than silently repair untrustworthy chronology. A reboot starts a new monotonic epoch. Close segments on lock/suspend; crash gaps remain unknown. NTP alone does not make timestamps tamper-proof. Record heartbeat health separately from work intervals.

Use half-open intervals `[start,end)`, split at local reporting-day boundaries using the site's IANA time zone, and preserve original UTC timestamps. Night shifts attach to explicit scheduled shift IDs, not an assumed calendar date. Daylight-saving dates can have non-24-hour days. Resolve overlapping devices/sessions by unioning coverage rather than summing duration; unresolved overlapping application/state evidence becomes a conflict bucket pending an audited correction. Keep observed interval, schedule, activity state and declared work context as separate dimensions. A meeting declaration does not transform a no-input interval into observed input activity. Track late data with report freshness/provisional markers and deterministic recomputation within the raw retention window; beyond that use an auditable correction process rather than accepting unrebuildable telemetry.

## Minimum data model

- Organization: employee, login principal, team, site/time zone, client/account, campaign, effective-dated memberships, device, device assignment, enrollment credential/revocation.
- Planning/context: shift, schedule version, employee assignment, leave, declared break/meeting/training, correction request/decision with original value and reason.
- Telemetry: immutable event, collector health, ingestion rejection, receipt, normalized state interval, reporting-day aggregate, processing job/checkpoint.
- Classifications: application registry, campaign-specific rule/version/effective dates; historic reports retain their original rule version unless explicitly recalculated.
- Output: import batch, source row/error, external employee mapping, work item or interval-level outcome fact, completed/accepted/reopened counts, handling seconds, quality denominator and score; unique source keys and explicit upsert/replacement semantics.
- Governance: role and scope grant, access/export audit, retention policy and purge run, metric definition/version, published report snapshot and freshness.

Use typed relational fields for critical identities, time and measures. Keep bounded JSON for versioned optional payloads only. Scope every report/export server-side by team/account authorization; enforce and test database access boundaries as defense in depth. Internal single-company use does not eliminate client confidentiality boundaries.

## Operational outcomes and imports

MVP imports CSV files for people/teams, schedules and operational results using documented templates. Validate headers, source IDs, types, time zones, units and employee mappings; preview rejects and totals before a privileged user commits; retain provenance and an import checksum. Reimporting a file is idempotent; replacement batches have explicit supersession history. Neutralize spreadsheet formula injection in exported strings. Do not store customer text or ticket bodies; use pseudonymous source keys where traceability is necessary.

AHT requires authoritative handling durations and a matching completed-handled-work denominator. Sequential status timestamps are not automatically handling time; simultaneous work makes inference particularly unsafe. Throughput and quality come from the CRM/telephony/QA source, not application focus. When authoritative data is absent, show unavailable and its reason. Activity coverage may help explain operations, but cannot establish billing leakage or payroll. Restrict the first operational dashboard to measurements whose numerator, denominator and source are defined and reconciled.

## Sizing and cost model

Illustrative model: 500 employees, 8 tracked hours/day, 22 working days/month and an average two application/state rows per 60-second bucket. In general, rows/day = employees x tracked hours x 60 x mean distinct application/state rows per bucket; retaining multiple subintervals can increase payload bytes even with a fixed row count. This is 480,000 events/day, 10.56 million/month, and approximately 16.7 inserts/second during the shared eight-hour shift. At a measured planning placeholder of 0.5-1.5 KB per event including indexes, raw storage is 5.3-15.8 GB per working month before WAL, backups, aggregates and free-space reserve. At 200 employees: 192,000/day; at 1,000: 960,000/day. Ten application/state rows per bucket multiplies all volumes by five. At 500 employees, one upload/minute is roughly 8.3 requests/second; fewer requests do not mean fewer events.

Start benchmarking on an available 4-vCPU, 16-GB RAM Linux VM with 150-250 GB SSD and independently stored backups. This is a proposed test allocation, not a capacity guarantee or purchase recommendation. Target 30 calendar days raw, 13 months daily aggregates and 90 days operational logs initially; governance can shorten these before collection. Budget replica/WAL/temp/index expansion and keep at least 30% disk headroom. A 30-day retention window includes weekends; calculate actual shifts rather than equating it with exactly 22 workdays in production forecasts.

Track actual allocated compute/storage, backup capacity, electricity/network, code signing, Windows test environment and IT maintenance time. Free licenses do not make total cost zero. Prefer existing identity, internal PKI and endpoint deployment tooling; never assume existing licenses or certificate availability. Keep production free of AI API charges; development AI usage is a separate budget already controlled by the user's account.

Load acceptance: agreed rollout population plus 2x normal steady traffic and a throttled full-population offline replay scenario; p95 common aggregate queries under 3 seconds, normal freshness under 5 minutes, no acknowledged event loss and duplicate-safe recomputation. Set bounded replay throughput so current data and reporting remain usable. Measure actual CPU, RAM, event bytes, WAL growth and worker backlog before rollout expansion.

Only reconsider additional infrastructure when indexing, aggregates, batch size, retention and query fixes have been measured and exhausted: persistent query/freshness SLO failure under expected load, storage growth exceeding the approved envelope, or unmanageable maintenance windows. Evaluate a larger existing VM first, then separation of worker/database, then analytic alternatives with an explicit total-cost comparison. ClickHouse remains deferred, including self-hosted ClickHouse, because it introduces another operational system even without a service bill.

## Operations and rollout gates

Reuse a verified company OIDC provider with MFA if available. If unavailable, isolate the prototype and choose an existing self-hosted/company authentication route during discovery; do not create a production password system casually. Separate human session auth from revocable per-device credentials; use short-lived enrollment tokens and credential rotation. Encrypt traffic, host disks and independent backups; keep recovery keys outside the failed host. Apply least privilege to API, workers, migrations and backup accounts. Audit administrator actions and exports without recording raw telemetry payloads in application logs.

One host is a deliberate cost/availability tradeoff. Initial production recovery objectives: RPO <=24 hours and RTO <=8 business hours, proven in a restore drill before rollout; analytics is not payroll-critical. Nightly backups to another physical/storage failure domain satisfy only that target. If the company needs a shorter RPO, configure base backups plus WAL archiving and measure archive lag; pg_dump alone cannot provide WAL-based point-in-time recovery. Back up deployment configuration and key recovery material separately. [PostgreSQL backup guidance](https://www.postgresql.org/docs/current/continuous-archiving.html)

Own operational runbooks: daily freshness/storage/backup review, monthly restore drill and dependency/OS patch review, quarterly access recertification. Alert on failed backups, full disk forecast, queue age, drift, endpoint health and import failure through existing internal channels. Test signed installer/update with a Windows test ring; verify signature/hash, prevent downgrade and exercise rollback. A signed binary does not guarantee antivirus acceptance. Do not promise tamper-proof monitoring against local administrators; report health gaps and manage endpoints through company policy.

Build order: (1) fixture data and definitions, (2) auth/scoping and import-to-report vertical slice, (3) Windows endpoint spike and offline ingestion, (4) reconciliation/corrections/security and load tests, (5) synthetic/test ring then 25-50 authorized employees, (6) an evidence-gated 200-employee rollout with a separate 1,000-employee capacity test before larger expansion. Human company authorization remains necessary for employee deployment and access to organizational systems; agents can autonomously prepare code, tests, documentation and review evidence.
